# Change log

## v0.22.2
### Breaking changes
- `Model.update(update, graph=G)` writes to `G`: `G` is the default graph of the update, as with `WITH <G>`, so triples without a `GRAPH` in the INSERT and DELETE templates, `INSERT DATA` and `DELETE DATA` are inserted into and deleted from `G`, and CLEAR DEFAULT clears it. Before, the WHERE clause was evaluated on `G`, but the triples were inserted into and deleted from the default graph. Updates sent to `Model.serve(graph=G)` (maplib Enterprise Edition) write to `G` in the same way
- A triple pattern whose predicate is in the maplib namespace (`https://datatreehouse.github.io/maplib/vocab#`), that no triples use and that is not a magic predicate of the build, is an error that names the predicate. It gave no solutions, silently, e.g. for a misspelt magic predicate, one that the build does not have, or `maplib:fts` without a full text index. The time series vocabulary (`maplib:hasTimeseries`, `maplib:hasDataPoint`, ...) is not checked
- `STRSTARTS`, `STRENDS` and `CONTAINS` with a second argument from the data that is not an `xsd:string` (an IRI, a number, an unbound value) give an unbound value, as SPARQL errors do, instead of failing the query. A constant of another type is still an error
### Features
- `query(bindings=...)` and `query_page(s)` take Python `bool`, `int` and `float` values, bound as `xsd:boolean`, `xsd:integer` and `xsd:double` literals. They were ignored, silently, so e.g. `FILTER(?v >= ?min)` with `bindings={"min": 10}` had no effect or no results. Values of other types raise an error
- `Model.update(..., bindings=...)` binds variables of the WHERE clauses and of the INSERT and DELETE templates, as `query(bindings=...)` does, so parameterised updates need no string templating. In Rust, `Model::update_keep_triples`, `Model::update_with_federation_keep_triples` and `Triplestore::update_keep_triples` take the bindings, and `query_processing::bindings::maybe_replace_bindings_update` replaces them in a parsed update
- DESCRIBE queries in `Model.query`, which raised "Query type not supported": the result is the triples whose subject is a described IRI (constant IRIs and the IRIs the described variables are bound to, or every variable for `DESCRIBE *`), as a CONSTRUCT result. Blank nodes are not described. This is what the SPARQL endpoint of `Model.serve` gives
- `REGEX` with a pattern or flags that differ per solution, e.g. `REGEX(?label, ?pattern)` or `REGEX(?v, CONCAT("^", ?prefix))`, and `STRBEFORE` and `STRAFTER` with a second argument that differs per solution. They raised "The following expression should resolve to a constant literal". An invalid pattern from the data gives an unbound value for its solutions, while an invalid constant pattern is still an error
### Features
- `GraphSnapshots(..., exclude_graphs=[None])` (maplib Enterprise Edition) leaves graphs out of the snapshot (None or `""` is the default graph): they are never written, restored or loaded from other writers, and writes to them are not pending. The next snapshot drops an existing entry of such a graph from the manifest, and `skipped_graphs` names the ones the last `restore()` did not load. `on_refresh(callback)` is called with the graphs other writers changed, under the write lock, so that an application can keep a graph it derives from them up to date. The writable Model portal (maplib Enterprise Edition) uses them with a Graph portal that rebuilds its default graph from the named graphs (`run_portal(rebuild_default_graph=True)`): the default graph, a copy of all uploaded data, is no longer written on every write, which rewrote a 27 MB file per upload for a default graph of 1.6M triples (274 ms locally, now 1 ms and 10 kB). Triples written only to the default graph are then not kept across restarts. `PORTAL_SNAPSHOT_DEFAULT_GRAPH=1` keeps it in the snapshot. In Rust, `GraphSnapshotOptions::exclude`, `GraphSnapshots::set_on_refresh`, `skipped_graphs` and `server::OnRefresh`
- The writable Model portal (maplib Enterprise Edition) answers a request that may write (POST, PUT, PATCH, DELETE, including SPARQL Update) only once its changes are published to `MODEL_URL`, at most `PORTAL_DURABLE_WRITE_TIMEOUT_SECONDS` (30) later, so that an acknowledged write survives a crash such as an OOM kill; the `X-Maplib-Snapshot` header of the answer says whether they were (`published`, `none`, `pending` or `failed`). Before, writes were published 2 to 7 s after they were answered. `PORTAL_DURABLE_WRITES=0` answers at once
### Features
- Prefixes in the config graph: `maplib.config.PrefixConfig`, `write_prefix`, `write_prefixes`, `read_prefixes`, `remove_prefix` and `apply_prefixes` keep the prefixes of a model in its config graph as SHACL prefix declarations (`sh:declare`, `sh:prefix`, `sh:namespace`) of the `owl:Ontology` `mcfg:prefixes`, so they travel with the model; `apply_config` adds them to the model (`Model.add_prefixes`). `generate_prefixes(m, graph=None, max_generated=8)` makes prefixes for the data in a graph (or a list of graphs): the usual prefixes of the well-known vocabularies it uses (`WELL_KNOWN_PREFIXES`: rdf, rdfs, xsd, owl, sh, skos, dcterms, prov, geo, cim, opc, ...) and short names for the other namespaces it uses most (`prefix_name_for`, `namespace_of`). See "Prefixes" in CONFIG_GRAPH.md
### Bug fixes
- Security advisories: the RDF/XML parser and the SPARQL XML results parser use quick-xml 0.41, which fixes quadratic run time on duplicate attribute checks (RUSTSEC-2026-0194) and unbounded memory for namespace declarations (RUSTSEC-2026-0195) on untrusted XML. `sparesults` is vendored in `lib/sparesults` for this, like `oxrdfxml`. zstd is updated to 0.13.4 (RUSTSEC-2026-0391, RUSTSEC-2026-0398, RUSTSEC-2026-0403 and the unsound zstd-safe advisories). In maplib Enterprise Edition, DuckDB is updated to 1.5.6 (duckdb crate 1.10506.1), whose build no longer uses zip 6 (RUSTSEC-2026-0367, -0368, -0369 and -0429)
- Comparisons (`<`, `<=`, `>`, `>=`) of string literals stored in the model, and `MIN` and `MAX` of stored strings and IRIs (also in window functions), used the order in which the values were first added to the model instead of codepoint order, e.g. `MIN(?label)` over `"urn:n/10"` and `"urn:n/1"` gave `"urn:n/10"`, and `FILTER(?a < ?b)` held for (`"urn:n/10"`, `"urn:n/1"`). `<` between string literals from VALUES was false in both directions. Strings computed in the query were not affected
- A variable whose name is another variable's name followed by `l`, `v`, `I`, `B` or `N` (e.g. `?o` and `?ol`) failed with "unable to find column" (and panicked in `Model.serve`) when `?o` holds values of several types, as with IRIs and literals: the internal columns of `?o`'s types had the other variable's name
- `m.add_graph(m, source_graph=..., target_graph=...)`, with the Model as its own source, raised an error (earlier: hung). It now copies the source graph into the target graph of the Model
- A SELECT query without variables, e.g. `SELECT * WHERE { <a> <p> <b> }`, gave an empty DataFrame also when the pattern matched. It now gives one row (with no columns) when it matches and none when it does not
- `SELECT (YEAR(?d) AS ?y) ... GROUP BY (YEAR(?d))` gave an unbound `?y`: an expression in the SELECT clause that is a GROUP BY expression is now the value of the group, as in other SPARQL engines
- `STRDT` with a lexical form that is not valid for the datatype failed the whole query ("Error parsing literal to target type in STRDT function"); it now leaves that solution's value unbound, as SPARQL errors do
- Polars Categorical and Enum columns, e.g. in the results of a Python virtualized database or in a DataFrame given to `map_triples`, are read as String columns. They failed with "Unknown datatype Categorical" (a panic for virtualized databases)
- maplib Enterprise Edition: every wheel includes the `cim` package. It was only added by the staging step of release builds, so other builds (e.g. `maturin develop`, the manylinux script and the benchmark image) left it out
### Performance
- `Model.map_json` and `Model.map_xml` with many documents (a list or iterable of strings or paths, eagerly or as a stream) add the triples of up to a thousand documents at once instead of one document at a time, which made mapping many small documents many times slower than mapping the same data as one document. The triples, their IRIs and the uuid namespace of each document are unchanged, and when a document fails, the documents before it are still mapped. In Rust, `Triplestore::map_documents` and `Model::map_documents` map several documents at once
- Reasoning and Datalog inference into a graph other than the one reasoned over (`Model.reason` into the transient graph or a `target_graph`, and SHACL rules, maplib Enterprise Edition) leave out the inferred triples that the graph already has while inserting them, by comparing the encoded triples, instead of running a SPARQL query for each predicate of each rule execution. The inferred triples are unchanged. In Rust, `Triplestore::add_triples_vec_excluding` and `insert_construct_result_excluding` add triples except those a graph already has
- `Model.reason` with `"owl-rl"` or `"rdfs-plus"` (maplib Enterprise Edition) handles `owl:sameAs` between individuals with a canonical representative per group of equal resources, found with union-find, instead of copying every triple to every equal resource in each round with SPARQL queries over all triples. The rules run on the triples of the representative, and its triples are copied to the other members of the group once at the end, so large groups no longer multiply the work of every round, and `eq-sym` and `eq-trans` are not run as rules. Groups with blank nodes, literals, classes, properties or other resources that the schema refers to are still replaced in every round. The inferred triples and violations are unchanged; the number of rounds and rule executions in the `ReasoningResult` can differ

## v0.22.1
### Breaking changes
- `Model.update` returns what the update changed instead of `None`, see Features. In Rust, `UpdateResult` has a `changes` field, and `Triplestore::delete_construct_result` and `delete_triples_vec` take `keep_triples` and return the deleted triples (`triplestore::changes::Deleted`) instead of nothing
- `IRI()`, `URI()` and `fn:castToIRI` give an unbound value for a string that is not a valid absolute IRI (a relative IRI, or one with spaces or other characters IRIs do not allow), as SPARQL 1.1 specifies for errors, instead of an invalid IRI term ([#60](https://github.com/DataTreehouse/maplib/issues/60))
- The time series virtualization vocabulary moved from the chrontext namespace (`https://github.com/DataTreehouse/chrontext#`) to the maplib vocabulary (`https://datatreehouse.github.io/maplib/vocab#`, prefix `maplib`): `maplib:hasTimeseries`, `maplib:hasDataPoint`, `maplib:hasTimestamp`, `maplib:hasValue`, `maplib:hasResource`, `maplib:hasExternalId`, and the functions `maplib:FloorDateTimeToSecondsInterval`, `maplib:dateBin`, `maplib:DateTimeAsMicros`, `maplib:MicrosAsDateTime`, `maplib:DateTimeAsSeconds`, `maplib:SecondsAsDateTime`, `maplib:modulus`, `maplib:time_bucket` and `maplib:nestAggregation`. None of the names clash with the existing terms of the vocabulary. The bundled templates and data (`maplib.ip21`, OSIsoft PI, Siemens Insights Hub, CDF, OPC UA, the config graph) use the new IRIs. `maplib.config.MAPLIB` is the namespace; `maplib.config.CHRONTEXT` is kept as a deprecated alias of it, and `maplib.config.LEGACY_CHRONTEXT` is the old namespace. In Rust, `representation::constants::LEGACY_CHRONTEXT_PREFIX_IRI` and `from_legacy_chrontext_iri` give the old namespace and its mapping.
- Deprecated: the old chrontext IRIs are still accepted and read as the maplib IRIs with the same local name: in SPARQL queries and updates (when parsing), in the predicates of data that is added or deserialized (they are stored as the maplib predicates, so queries and exports show the new IRIs), and in the templates of virtualizations. The `chrontext` prefix that `map_osipi` and `map_insights_hub` add still points to the old namespace, next to `maplib`. IRIs of the old namespace in the object position of data (e.g. `sh:path` in a shapes graph) are not rewritten. Custom Python virtualized databases that compare function IRIs, e.g. with `https://github.com/DataTreehouse/chrontext#FloorDateTimeToSecondsInterval`, now get the maplib IRI and must compare with that.
- AVG over values of one integer type is an `xsd:decimal`, as SPARQL defines it, and AVG over `xsd:float` values is an `xsd:float`. It kept the type of its input, so the average was right but expressions using it were computed in integers: `MAX(?x) - AVG(?x)` over 1, 2, 3 and 3 gave 1 instead of 1.25
### Features
- Reasoning profiles (maplib Enterprise Edition): `Model.reason(profile="owl-rl" | "rdfs-plus" | "rdfs", graph=None, target_graph=None, include_graphs=None, max_violations=1000)` materializes the entailments of a built-in ruleset with the Datalog engine and returns a `ReasoningResult` with the number of inferred triples and the violations found. `"owl-rl"` implements the OWL 2 RL/RDF rules of OWL 2 Profiles (section 4.3), including `owl:propertyChainAxiom`, `owl:hasKey`, `owl:intersectionOf`, `owl:unionOf`, `owl:oneOf`, the RL forms of `owl:someValuesFrom`, `owl:allValuesFrom` and `owl:hasValue`, and max (qualified) cardinality 1, but not eq-ref (every term `owl:sameAs` itself) and the datatype rules other than dt-type1. The rules with `false` in the head (e.g. cax-dw, prp-irp, cls-nothing2, eq-diff1) are checked after inference, and their matches are returned in `ReasoningResult.violations` as dicts with the rule name, a message and the terms. `"rdfs-plus"` is a cheaper preset in the style of GraphDB's RDFS-Plus (optimized): the RDFS rules without axiomatic and reflexive triples, with `owl:inverseOf`, `owl:SymmetricProperty`, `owl:TransitiveProperty`, `owl:equivalentClass`, `owl:equivalentProperty`, `owl:sameAs`, `owl:FunctionalProperty` and `owl:InverseFunctionalProperty`. `"rdfs"` implements the RDFS entailment rules of RDF 1.1 Semantics (rdfD2 and rdfs1 to rdfs13 with the axiomatic triples), except rdfs4a and rdfs4b. The inferred triples go to the transient graph by default, or to `target_graph`, and triples that are already in the graph are not added again. The schema is compiled into rules with constant predicates (one or two per property, and one per restriction, chain or key) that the Datalog engine evaluates semi-naively, the equality replacement rules are applied with SPARQL when `owl:sameAs` triples exist, and both are repeated until the schema no longer changes. The W3C OWL 2 RL test cases, the RDF 1.1 Semantics entailment tests and the SPARQL 1.1 entailment regime tests are included in the tests, see `w3c_owl2_rl_known_failures.txt`, `w3c_rdf_mt_known_failures.txt` and `w3c_sparql11_entailment_known_failures.txt` for the tests that do not pass. In Rust this is `datalog::reasoning::reason` and `Model::reason`
- R2RML: `Model.map_r2rml(mapping, database=None, tables=None, base_iri=None, graph=None, ignore_data_errors=False)` maps relational data with a W3C R2RML mapping. Each logical table (`rr:tableName` or `rr:sqlQuery`) is queried once, from a database in `maplib.virtualization`, a DuckDB connection or polars DataFrames given in `tables`, and the term maps are evaluated column by column in parallel, so no rows are handled one by one in Python. It supports constant, column and template term maps, term types, languages, datatypes, `rr:class`, graph maps and referencing object maps with join conditions, and is tested with the W3C R2RML test cases
- Microsoft Fabric (maplib Enterprise Edition): `Model.map_fabric(ontology, lakehouse=None, eventhouse=None, ...)` maps a Fabric IQ ontology to OWL, maps the data bound to it from the lakehouse with a generated R2RML mapping (which it returns), and virtualizes its time series, queried in SQL in the lakehouse or in KQL in the eventhouse. The open-source build raises `NotImplementedError`
- Window functions in SPARQL queries ([w3c-cg/sparql-dev#47](https://github.com/w3c-cg/sparql-dev/issues/47)), with the SQL syntax proposed there: `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, and `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `SAMPLE` and `GROUP_CONCAT` followed by `OVER (PARTITION BY ... ORDER BY ... ROWS BETWEEN ... AND ...)`, where each part is optional, e.g. `BIND(ROW_NUMBER() OVER (PARTITION BY ?group ORDER BY DESC(?value)) AS ?rank)`. They can be used wherever an expression can: in a SELECT expression, BIND, FILTER and HAVING, and over aggregates in a grouped query (`RANK() OVER (ORDER BY DESC(COUNT(*)))`). A window function is computed over the solutions of the pattern it is evaluated on: the group of a BIND or FILTER, before it is joined with the rest of the query, or the solutions of the query (after GROUP BY) for SELECT and HAVING, so `HAVING (ROW_NUMBER() OVER (PARTITION BY ?g ORDER BY DESC(?v)) <= 3)` without GROUP BY selects the top three of each group. As a FILTER applies to its whole group, a window in a BIND also sees the solutions that a FILTER of the same group removes; put the FILTER in a nested group to apply it first. `FILTER(?r = 1)` on a `RANK` or `DENSE_RANK` with one ordering key keeps the first rows of each partition without ranking them. The semantics are those of SQL: ORDER BY orders as the ORDER BY of SPARQL (unbound values first, values of different types as there), rows with equal keys are peers that get the same RANK and DENSE_RANK, unbound PARTITION BY values form a partition, aggregates without ORDER BY are over the whole partition, aggregates with ORDER BY are running aggregates up to and including the peers of the row, and `ROWS` frames (`n PRECEDING`, `CURRENT ROW`, `n FOLLOWING`, `UNBOUNDED`) count rows. The aggregates follow the types and numeric promotion of the same aggregates in GROUP BY, also for values of several types. RANGE and GROUPS frames are not supported
- ORDER BY in GROUP_CONCAT, SAMPLE and custom aggregates ([w3c-cg/sparql-dev#9](https://github.com/w3c-cg/sparql-dev/issues/9)): `GROUP_CONCAT(?x; SEPARATOR=", " ORDER BY ?y DESC(?z))` joins the values in that order, `SAMPLE(?x ORDER BY DESC(?y))` takes the first value in that order. The `ORDER BY` may follow the expression or the separator, with or without a `;`, or precede the separator (`GROUP_CONCAT(?x; ORDER BY ?y; SEPARATOR=".")`, as in the prototype tests of the SPARQL 1.2 community group, which are included in the tests). With DISTINCT, the first occurrence of each value in the order is kept. In Rust, window calls and ordered aggregates are represented in the algebra as calls to reserved functions in the maplib namespace, see `spargebra::window`, so that the algebra types are unchanged
- `LATERAL` (correlated subqueries, [SEP-0006](https://github.com/w3c/sparql-dev/blob/main/SEP/SEP-0006/sep-0006.md)): in `?s a :T LATERAL { SELECT ?s ?o WHERE { ?s :p ?o } ORDER BY DESC(?o) LIMIT 3 }` the group after `LATERAL` is evaluated for every solution of the pattern before it, with that solution's variables substituted, so it gives e.g. the top N per entity or an aggregate per entity. A sub-select substitutes only the variables it projects; the others are variables of the sub-select. A variable that is unbound in a left solution is not substituted for it. The right side may not bind a variable of the left side again. The right side is evaluated once for all left solutions together rather than once per solution: ORDER BY with LIMIT and OFFSET slices, GROUP BY groups, and DISTINCT deduplicates for each left solution separately. To aggregate per left solution over a correlated variable that is only used in a FILTER, project it and GROUP BY it, as SPARQL does not allow projecting an ungrouped variable next to an aggregate. The LATERAL tests of Apache Jena and Oxigraph are included in the tests
- GRAPH blocks in CONSTRUCT templates ([w3c/sparql-dev#31](https://github.com/w3c/sparql-dev/issues/31)), with the syntax of Apache Jena and of INSERT templates: `CONSTRUCT { ?s ex:r ?o GRAPH ex:g { ?s ex:q ?o } GRAPH ?g2 { ?o ex:q ?s } } WHERE { ... }`. The graph is an IRI or a variable; with a variable, each solution gives triples in the graph that the variable is bound to, and solutions where it is unbound or not an IRI give none. `Model.insert` and `ModelStream.insert` add the triples of each GRAPH block to its graph, and the other triples to `target_graph` (the default graph if not given), all in one go, so the WHERE clause is evaluated once instead of once per graph. `Model.query` returns one DataFrame per template triple (and graph) as before, and the DataFrames from GRAPH blocks have an extra `graph` column with the IRI of the graph; `return_format="trig"` returns the result as TriG, and `"turtle"` raises an error when the result has triples in named graphs. The short form `CONSTRUCT WHERE { GRAPH ?g { ... } }` is also supported. Blank nodes in the template are shared between its GRAPH blocks. In Rust, `Query::Construct` has a new `graph_template: Vec<QuadPattern>` with the triples of the GRAPH blocks, `QueryResultKind::Construct` holds `ConstructedTriples` with the graph of each part, `template_to_solution_mappings` returns them in template order, and `Triplestore::insert_constructed_triples` inserts them. Jena ARQ's syntax tests for CONSTRUCT quads are included in the tests, except two that use Jena's bare `{ ... }` blocks in templates
- Revealing update effects ([w3c-cg/sparql-dev#63](https://github.com/w3c-cg/sparql-dev/issues/63)): `Model.update` returns, per graph (keyed by IRI, `DEFAULT_GRAPH` for the default graph), the number of triples that were really inserted and deleted: triples that were already present are not counted as inserted, and triples that were absent are not counted as deleted. This covers INSERT DATA, DELETE DATA, DELETE/INSERT WHERE, DELETE WHERE, CLEAR and DROP; the changes of the operations of an update are summed. The counts come from the deduplication and deletion that the update does anyway, so they cost nothing extra. With `return_triples=True` the result also holds the inserted and deleted triples as DataFrames per predicate (or SolutionMappings with `solution_mappings=True`), which costs an extra pass over the tables that triples are deleted from. The SPARQL endpoint of `Model.serve` (maplib Enterprise Edition) sends the counts as JSON (`{"graphs": [{"graph": ..., "inserted": ..., "deleted": ...}]}`, with `null` for the default graph) to update requests that accept `application/json`, and still answers others with no content; the Flight update action includes them in its result. In Rust, `Model::update_keep_triples`, `Model::update_with_federation_keep_triples` and `Triplestore::update_keep_triples` keep the triples
- Vector literals: the datatype `maplib:vector` (`https://datatreehouse.github.io/maplib/vocab#vector`) holds embeddings, with the components as a list of numbers in square brackets, e.g. `"[0.12, -0.5, 3e-4]"^^maplib:vector`. In `Model.map` and `Model.map_triples`, Polars columns of fixed size arrays of numbers (`pl.Array(pl.Float32, 384)`) are mapped to vector literals. In Rust, `representation::vectors` has the datatype and the conversions
- Vector search (maplib Enterprise Edition): enable it with `IndexingOptions(vectors=True)`. The vectors of vector literals are indexed by predicate, and the magic predicate `maplib:vectorSearch` finds the triples whose vector literal is nearest to a query vector: `?s maplib:vectorSearch [ maplib:vectorQuery "[...]"^^maplib:vector ; maplib:vectorLimit 10 ; maplib:vectorScore ?score ]`. The query is a vector literal, a string with the lexical form of one, or an IRI, whose own vector is then used ("more like this"). The optional arguments are `maplib:vectorMetric` (`"cosine"`, the default, `"dot"` or `"euclidean"`), `maplib:vectorPredicate` (an IRI to search one predicate, or a variable to bind it), `maplib:vectorObject` (binds the vector literal), `maplib:vectorScore` (the cosine similarity, dot product or Euclidean distance) and `maplib:vectorExact`. A constant subject restricts the search to that subject. The search is exact by default. With `IndexingOptions(vector_ann=True)` an approximate nearest neighbour index is also built and kept up to date as triples are added; cosine searches then use it unless `maplib:vectorExact true` is given, and `maplib:vectorCandidates` (default 64) trades speed for recall. The functions `maplib:cosineSimilarity`, `maplib:dotProduct` and `maplib:euclideanDistance` compare two vectors anywhere in a query, e.g. in `BIND`, `FILTER` and `ORDER BY`, and use the indexed vectors of stored vector literals when there is an index. The index is rebuilt from the triples on compaction and deserialization, and like the full text search index it is not updated when triples are deleted
- Streams can iterate on a persistent Model: with `in_place=True` on `Model.map`, `map_triples`, `map_default`, `map_json` or `map_xml` (with `stream=True`), every batch is mapped into the Model itself and the steps run on it, so updates, inserts and rules join the batch with the Model's other graphs and their results are kept. Batches run one at a time under the Model's write lock, released between batches. The new `ModelStream.drop_graphs(graphs)` step removes the per-batch graphs, and it still runs when an earlier step of the batch fails. When collected, an in-place stream checks that the graphs named in `drop_graphs` steps are empty and that write steps only write graphs that a later `drop_graphs` step drops (or the transient graph). `compact_every=N` compacts the Model and removes unused dictionary entries every N batches
- `Model.drop_graphs(graphs)` removes graphs with their full text and vector indexes, and in disk storage mode deletes the files of their triple tables. `with m.scratch_graphs(g1, g2):` drops the graphs when the block exits, also on an error. In Rust, `Triplestore::drop_graphs`
- Outbound connection policy (against server-side request forgery, SSRF): `maplib.set_outbound_policy(mode="any" | "public" | "allowlist", allow=[...], check=None)` is one place where an application decides which hosts maplib may connect to. maplib checks the final scheme, host and port of every connection it makes for a configuration, a query or a server's answer before connecting: the databases of `maplib.config` (`probe`, `apply_virtualization`, `apply_config`, from the host the database builds, e.g. `<account>.snowflakecomputing.com` for a Snowflake account, the OneLake endpoint of a Fabric lakehouse, the cluster URI of Kusto, the `base_url` and `token_url` of Cognite Data Fusion, the derived token endpoint of Insights Hub), the databases of `maplib.virtualization`, `Model.map_osipi`, `map_pi_points`, `map_insights_hub` and `map_cdf`, IP.21, OPC UA, `Model.query_external` and `Model.query(endpoint=...)`. The host is resolved and every address it resolves to is checked. `public` refuses loopback, private, link-local and other non-public addresses, and `allowlist` allows only the hosts in `allow`; `allow` takes host names, `*.domain`, addresses and CIDR ranges, which are allowed in every mode. Cloud metadata services (169.254.169.254, fd00:ec2::254, 100.100.100.200, 169.254.170.2, 192.0.0.192, metadata.google.internal) are refused in every mode, also by default and when listed. Redirects are checked by the clients maplib controls (urllib, requests and reqwest, whose DNS resolver also checks the addresses it connects to, against DNS rebinding); the absolute URLs of PI Web API links are checked too. `check(scheme, host, port)` is called after these checks for connections made from Python. Refusals raise `maplib.OutboundError`, a `PermissionError`. `maplib.outbound` also has `check_url`, `check_host`, `check_connection`, `connection_targets`, `urlopen` and `guard_session` for applications and database classes of their own. In Rust, the new `outbound` crate (`outbound::check`, `check_url`, `set_policy`, and with the `reqwest` feature `guard_client`)
- Keyset pagination ([sparql-dev#49](https://github.com/w3c-cg/sparql-dev/issues/49)): `Model.query_pages(query, page_size=10000)` iterates over the pages of a SELECT query, and `Model.query_page(query, page_size, page_token)` gives one page and the token of the next. Each page starts after the last solution of the previous page, instead of skipping the solutions before it with OFFSET, so a page deep into a large result costs no more than the first. The solutions are ordered by the ORDER BY of the query and then by the projected variables, so the order is total and the pages put together are the result of the query without duplicates or gaps (a query without ORDER BY is ordered by its projected variables). Duplicate solutions are counted across pages, and the LIMIT and OFFSET of the query apply to the pages as a whole. Pages are evaluated one at a time and see the model as it is then: no solution is returned twice, solutions in the result throughout are returned exactly once, removed solutions are not returned once removed, and added solutions are returned when they sort after the last solution returned. A page token (`QueryPages.token`) is a string safe in URLs that holds the position, not the results, so it can be kept and used later or in another process; it is refused for another query. SELECT DISTINCT can be paged when its ORDER BY uses only projected variables. With `return_format="json"`, pages are SPARQL 1.1 JSON results. Queries of models with virtualized databases can not be paged yet. In Rust, `Model::query_page` and `Triplestore::query_page` take a `PageCursor` (`triplestore::sparql::paging`)
- `Model.serve()` (maplib Enterprise Edition) takes `page_size` and `page_token` parameters on the SPARQL query endpoints: a SELECT query gives that page of its solutions, and the token of the next page in the `Next-Page-Token` response header, which is absent on the last page (exposed to CORS clients). `limit` and `offset` parameters apply a LIMIT and an OFFSET after those of the query ([sparql-dev#91](https://github.com/w3c-cg/sparql-dev/issues/91)). Pages are not kept in the query result cache, whose key includes `limit` and `offset`.
- Statistical aggregates from Apache Jena ARQ: `agg:stdev`, `agg:stdev_samp`, `agg:stdev_pop`, `agg:variance`, `agg:var_samp` and `agg:var_pop` in `http://jena.apache.org/ARQ/function/aggregate#`, also available in `http://jena.apache.org/ARQ/function#` as in Jena. They return an `xsd:double`, take `DISTINCT`, and can be used in HAVING and as window functions (`agg:stdev(?x) OVER (PARTITION BY ?g ORDER BY ?t ROWS BETWEEN 9 PRECEDING AND CURRENT ROW)`). A group with a non-numeric value, with no values, or with a single value for the sample statistics gives an unbound result, as in Jena. Jena's tests for them (TestStatisticsAggregates) are ported, and the results are checked against Python's `statistics` module. See "Statistical aggregates" in API_USAGE.md
- SHACL entailment (maplib Enterprise Edition): a shapes graph's `sh:entailment` is honoured. For RDFS, validation first materializes the RDFS entailments with `Model.reason`'s `"rdfs"` profile, and for the OWL regimes (OWL 2 RDF-Based and Direct semantics) the `"owl-rl"` profile, into a temporary graph that rules and constraints read, which is removed afterwards. Simple entailment, `sh:RulesEntailment`, `sh:Rules` and `sh:RuleSet` need no reasoning, and other regimes (D, RIF, ...) make validation fail instead of being ignored. Shapes graphs that declare RDFS entailment may now report more results, e.g. for `rdfs:Resource`

- `Model.update` reports the triples that LOAD inserts, in the graphs they went to; they were left out of the changes

INSERT and DELETE templates are unchanged, as SPARQL 1.1 does not allow these blocks there

In disk storage the parquet files of the removed tables are deleted from the storage folder; files a model was deserialized from are never touched. The W3C SPARQL 1.1 Update tests now run in all three storage modes
- Vector search (maplib Enterprise Edition) and the vector functions now agree with numpy and scipy on edge cases. Euclidean search is computed from the component differences, so near-duplicate vectors far from the origin are ranked correctly and a stored vector is at distance 0 from itself. Zero vectors and vectors with NaN or infinite components have no cosine similarity, so cosine searches leave them out (they were returned with a score of 0), and a zero query vector finds nothing. Vectors at an infinite distance or dot product are no longer dropped when fewer than `maplib:vectorLimit` results are found. `maplib:cosineSimilarity`, `maplib:dotProduct` and `maplib:euclideanDistance` compute in 64 bit floats, so very small or large components no longer underflow or overflow. Tests now check the functions against scipy, exact search against numpy and faiss, and the recall of the approximate index against hnswlib with the same parameters
- The FILTER of an OPTIONAL can use variables that only the pattern before the OPTIONAL binds, as in `?s :min ?min OPTIONAL { ?s :v ?v FILTER(?v > ?min) }`. It used to be evaluated without those variables, so no optional match passed it and the variables of the OPTIONAL were always unbound
- A SHACL SPARQL rule (maplib Enterprise Edition) whose `sh:construct` has GRAPH blocks in its template raises an error, as Datalog rules do. The graphs were ignored and the triples went to the inferences graph
- `GraphSnapshots.restore()` (maplib Enterprise Edition, the writable Model portal) no longer adds the snapshot's copy of a graph to a graph of the same name that the model already has, e.g. shapes loaded by the entry point before restoring: the blank nodes of such graphs were duplicated on every start and every new replica. The model's own copy is kept, and when it differs from the snapshot's, the next snapshot publishes it
- After `GraphSnapshots.restore()`, the first snapshot no longer writes every graph again: graphs that were restored, or loaded before restoring, count as published, and a write that leaves their content unchanged (building an index, as the Model portal does at start, marks every graph as written) is not published
- The background loop of `GraphSnapshots` (and the writable Model portal) backs off when the store fails, e.g. a missing bucket or container, or auth or network errors: it waits `backoff_min` (1 s), doubling with each failure in a row up to `backoff_max` (300 s), with jitter, instead of trying about once a second, and logs one warning per try on the `maplib.graph_snapshots` logger. A success resets it, and `stop()` (the snapshot on SIGTERM) tries at once
- SAMPLE skips unbound values, so it gives a value whenever the group has one, also with ORDER BY (`SAMPLE(?x ORDER BY ?y)` is the first bound value in that order)
- AVG of no values (a group where the expression is never bound) is 0, as SPARQL 1.1 defines it, instead of unbound; also for AVG over a window
- ORDER BY orders numbers of different datatypes by value, as the `<` operator compares them, instead of grouping them by datatype first (`1` before `1.5` before `2` for an integer, a decimal and an integer). Numbers that a double cannot tell apart keep their exact order
- `COUNT(?x)` and `COUNT(DISTINCT ?x)` skip unbound values; `COUNT(DISTINCT ?x)` counted them as one extra value
- `FILTER NOT EXISTS` and `FILTER EXISTS` give the right result in groups with a variable predicate pattern: the filter pushdown rewrite moved them below the patterns that bind their variables, so they were evaluated without those bindings
- JSON-LD output keeps IRIs whose local part would start with `/` uncompacted: `ex:/a` would be read back as a different, absolute IRI
- `maplib.storage` gives the same version token, the unquoted ETag, from `head`, `get`, `list` and `put` on every backend, so a token from any of them works with `put(if_match=...)`
- `ModelStream.collect()` hands its blank node counters back to the Model, also when it fails, so a later stream or mapping from the same Model no longer reuses blank node labels that an earlier stream wrote (two streams of a template with a blank node both wrote `_:b_l0_p0_r0`, which merged distinct nodes when the outputs were combined)
- A variable that an OPTIONAL or a UNION branch may leave unbound, and that other patterns of the group also use, is joined as compatible with any value, as SPARQL specifies; such solutions were lost or joined wrongly when the OPTIONAL or UNION came first in its group. The W3C tests `service4a` and `values7` pass
- `maplib:path` and `maplib:shortestPath` patterns are joined after the other patterns of their group, so they get their start and target nodes from them wherever they are written
- Parsing `REGEX`, `SUBSTR` and `REPLACE` takes time linear in their nesting depth; nested calls (e.g. the about 20 nested `REPLACE` calls that `map_csvw` generates for some tables) took exponential time and could overflow the stack. `map_csvw` also runs on a large stack
- A `Model` stays usable after a call panics: every Python method recovers the model's lock instead of raising on a poisoned lock
- Virtualized time series queries (maplib Enterprise Edition) give the same results as the equivalent queries over materialized data in more cases: subqueries in joins (with LIMIT, DISTINCT or hidden variables), GROUP BY on a virtualized value such as the timestamp, aggregates without GROUP BY over no rows (one row, e.g. a count of 0), several data point patterns of one time series, and data points written without their time series. A differential test against materialized data now passes for all of its queries
- SHACL reports (maplib Enterprise Edition) hold the whole `sh:resultPath` of a result with a complex path (a sequence, alternative, inverse or zero-or-more path, i.e. a blank node of the shapes graph): its triples are copied from the shapes graph into the report graph, where the path was a dangling blank node
- `GRAPH ?g { ... }` on a model or dataset without named graphs keeps `?g` in scope, so `GROUP BY ?g`, ORDER BY or projecting `?g` give an empty result instead of an error that `?g` is not defined

## v0.22.0
### Breaking changes
- `xsd:dateTime` and `xsd:dateTimeStamp` values are all stored as UTC instants (Polars `Datetime("us", "UTC")`), and the time zone offset of a literal stays part of its type. Naive datetime columns of mapped DataFrames used to be stored as naive datetimes, so comparing, joining or unioning them with other dateTimes failed ("could not evaluate '>=' comparison between Datetime('μs') and Datetime('μs','UTC')", "failed to determine supertype", or a panic when such a CONSTRUCT or UPDATE wrote to a named graph). They are now read as UTC wall clock times and still have no time zone: they serialize as before (`"2026-11-14T06:12:00"^^xsd:dateTime`), but query results return them as UTC-aware datetimes (`datetime[μs, UTC]`, `tzinfo=timezone.utc` in Python) instead of naive ones, as dateTimes read from RDF files already were. Time zone aware columns in other time zones are converted to UTC. Models serialized by earlier versions load and serialize the same, and their naive dateTimes are read as UTC wall clock times, so they also come back UTC-aware and now compare with other dateTimes. Casting a string to `xsd:dateTime` accepts `Z` and offsets such as `+02:00`, which used to be an error, and gives the UTC instant without a time zone in its type (`xsd:dateTime("2026-11-14T08:12:00+02:00")` is `"2026-11-14T06:12:00"^^xsd:dateTime`), so it equals dateTimes without a time zone, not those with one. Strings that are not dateTimes give unbound instead of an error. `chrontext:MicrosAsDateTime`, `chrontext:SecondsAsDateTime` and `chrontext:FloorDateTimeToSecondsInterval` return UTC-aware datetimes
- SHACL rules (maplib Enterprise Edition) follow SHACL 1.2 Inference Rules: rules that no shape links to with `sh:rule` (global rules) also run, `sh:condition` restricts the focus nodes to those conforming to the condition shapes, `sh:deactivated` rules are skipped, and rules run in ascending `sh:layer` and `sh:order`, where rules with the same order do not see each other's new triples within an iteration. Rule types other than `sh:SPARQLRule`, `sh:TripleRule` and SPARQL rule templates, and any `sh:ruleProcessor`, are errors. The `rule_log` of the validation report lists the layer instead of the number of targets
- Transient triples are removed. Triples that should be available for querying, validation and reasoning, but not written, now go in a reserved named graph, `maplib.TRANSIENT_GRAPH` (`https://datatreehouse.github.io/maplib/vocab#TransientGraph`). The `transient` parameter of `map_json`, `map_xml`, `read`, `reads` and `insert` is removed: pass `graph=TRANSIENT_GRAPH` (or `target_graph=TRANSIENT_GRAPH` for `insert`) instead
- `include_transient` is replaced by `include_graphs: Optional[List[str]]` in `query`, `update`, `insert`, `infer`, `get_predicate`, `get_predicate_iris` and the corresponding `ModelStream` steps. The included graphs are merged into the queried graph, as with FROM. For `query`, `update`, `insert` and `infer`, `None` includes the transient graph (as `include_transient=True` did) and `[]` includes nothing; for `get_predicate` and `get_predicate_iris`, `None` includes nothing. `GRAPH ?g` ranges over the transient graph as over any other named graph, and `GRAPH <g>` no longer sees transient triples added to `g`
- RDFS inference (`infer_rdfs`) and SHACL rules (without an `inferences_graph` equal to the data graph) put their inferred triples in the transient graph. Writing all graphs as TriG or N-Quads leaves out the transient graph; write it with `graph=TRANSIENT_GRAPH`
- In Rust, `QuerySettings::include_transient` is replaced by `include_graphs: Vec<NamedGraph>`, and the `transient` arguments of the triplestore and model methods are removed. `NamedGraph::transient()` gives the transient graph
- The `message` column of `ValidationReport.results()` and `details()` is a list of strings, one per `sh:message` of the shape or SPARQL constraint (`"value"@lang` for language tagged strings, the value for plain strings), and null when there are none. Use e.g. `.explode("message")` to get one row per message
- `Model.serialize` writes a single file by default, and the default path of `Model.serialize` and `Model.deserialize` is `./model.maplib` instead of `./serialized_triples`. Pass `single_file=False` to write a folder as before
- In Rust, `Model::expand_default`, `expand_default_first_batch` and `expand_default_batch` take the key columns as `&str` and `&[String]`, and a nested (List or Struct) key column is an error instead of a panic
- The `max_results` parameter of `Model.infer` and `ModelStream.infer`, and the `max_shape_constraint_results` parameter of `Model.validate`, are removed: the memory limit (`maplib.set_memory_limit`) bounds inference and validation instead. `max_iterations` and `max_rows` are unchanged. In Rust, `Model::infer` and `Model::validate` no longer take them
### Features
- `Model.generate_template(data, primary_key_column)` is a dry run of `Model.map_default`: it returns the default template that `map_default` would map with, as a stOTTR string, without mapping the data or adding the template to the model. Review or edit it and map with `m.map(template, data)`. `map_default` generates its template with the same code (`maplib::model::default::generate_default_template` in Rust), so the two agree
- `maplib.GraphSnapshots(model, url, ...)` (maplib Enterprise Edition) keeps a model in storage as one HDT file per named graph and a `manifest.json`, which several writers can share: only the graphs that changed are written (found from the model's own writes), the manifest is published with a conditional put, and a writer that loses the put merges the graphs both sides changed three-way at the triple level. `restore()`, `snapshot()`, `refresh()`, `gc()` and a background loop with `start()` / `stop()`. `Model.serve(snapshot_format="graphs", refresh_interval=10)` serves a model kept this way. The writable Model portal uses it, in place of its Python implementation. In Rust, `VersionTable::changed_graphs_since` and `graph_stamp` give the graphs written after a stamp, and `RemoteError::is_not_found` and `is_precondition_failed` classify object storage errors
- `Model.serve(snapshot_url=..., snapshot_interval=900, storage_options=None)` (maplib Enterprise Edition) snapshots the served model with `Model.serialize`: every `snapshot_interval` seconds if it changed since the last snapshot (through the endpoints or from Python), and when the server stops. An unchanged model is never written. `python -m maplib.serve` serves a serialized model configured with environment variables (`MODEL_URL`, `ALLOW_UPDATE`, `SNAPSHOT_URL`, ...) and takes the last snapshot on SIGTERM; the cloud deploy recipe (now in maplib Enterprise Edition) runs it
- Query timeouts and cancellation: `Model.query(timeout=...)` and `Model.update(timeout=...)` (seconds) stop the query when its time is up and raise `maplib.QueryTimeoutError` (a `MaplibException`). Queries are checked between operators, after every join while it produces rows (also on the streaming engine), while waiting for Polars collects, and in path searches and property paths, and while results are formatted (Model.query) or serialized (the server); a query with a timeout and a join that may give many rows is collected with the streaming engine, which can stop a running join. So a query that would run for hours or exhaust memory, such as a cross join of three triple patterns, stops within a fraction of a second of its timeout. Other queries running at the same time are not affected (Polars' own abort, used for Ctrl-C, stops every query in the process). An update is checked before each operation and while its WHERE clause is evaluated, and its writes are never stopped halfway: operations of the request done before the timeout stay done. `Model.serve(query_timeout=...)` (maplib Enterprise Edition) limits every query and update through the endpoints, counted from when the request arrives, and requests can ask for less with the `timeout` parameter (seconds; URL or form parameter, the `X-Maplib-Timeout` header, or `"timeout"` in Arrow API and Flight commands and Flight update actions), or more up to `max_query_timeout`. A query that times out is answered with 503 Service Unavailable (Flight: `DEADLINE_EXCEEDED`), and a query whose client disconnects is cancelled, so it no longer runs on after its client gave up. `max_concurrent` (64 by default) limits the operations on the model that run at once; waiting for a turn counts towards the timeout. `Model.query(endpoint=..., timeout=...)` sends the timeout to the server and raises `QueryTimeoutError` when the server stops the query. In Rust, `utils::cancel::CancelToken` is a deadline and a cancel flag, made current for a thread with `utils::cancel::with_token`; `SparqlError::Cancelled` and `InterruptableCollectError::Cancelled` report a stopped query, and `ServerOptions` has `query_timeout`, `max_query_timeout` and `max_concurrent`
- Query result cache: `Model.set_query_cache(QueryCacheOptions(...))` keeps the results of `Model.query` and of the SPARQL protocol endpoints of `Model.serve`, which share it. A result is kept until a write changes the triples it can read: every write records the named graphs and predicates it changed, and every query reads a set of (graph, predicate) pairs found from its algebra, so writes to other graphs or other predicates keep it. Variable predicates, negated property sets, zero-length paths between variables, full text search and DESCRIBE read every predicate of their graphs, and `GRAPH ?g` reads a predicate in every graph. Changes of the prefixes, the indexing options, user defined functions and virtualizations invalidate everything. Queries calling NOW(), RAND(), UUID(), STRUUID(), BNODE() or user defined functions, with `parameters`, with `debug` or reading virtualized databases (unless `cache_virtualized=True`) are never cached. The options are on or off, the largest number of results, their total size, the largest result kept, a ttl, the shortest run time worth keeping and whether to keep results over virtualized databases, and can be changed at any time. Cached results are answered without waiting for a write that runs elsewhere in the model, and the server answers them without holding the GIL. `Model.query(cache=False)` skips the cache, `Model.query_cache_stats()` gives its counts (hits, misses, evictions, invalidations, size) and `Model.clear_query_cache()` empties it. The cache is off by default. `Model.serve(query_cache=...)` sets it for the server, which reports `X-Maplib-Cache: hit | miss | bypass` on each response, a `cache` field on each query log entry, cache totals and hit rates in `/query-log` and the cache's counts in `/status`. In Rust, `Triplestore::query_cache` (`triplestore::query_cache::QueryCache`), `Model::cache_plan`, `Model::add_prefixes` and `ServerOptions::query_cache`
- SHACL rules (maplib Enterprise Edition) implement SHACL Advanced Features and SHACL 1.2 Inference Rules: `sh:SPARQLRule` (shape rules with `$this` pre-bound to each focus node, and global rules), `sh:TripleRule` with node expressions (focus node, constants, lists, path values with `shnex:pathValues` or `sh:path`, `exists`, `if`, `distinct`, `intersection`, `union`/`concat`, `remove`, `filterShape`, `instancesOf`, `count`, `sum`, `min`, `max` the `sparql:` functions and SHACL-AF `sh:SPARQLFunction` calls), SPARQL rule templates (`sh:SPARQLRuleTemplate` with `sh:parameter`), `sh:condition`, `sh:deactivated`, `sh:order`, `sh:layer`, `sh:runOnce`, rule sets (`sh:RuleSet`, `sh:hasRule`, `sh:includesRuleSet`) selected with `sh:entailment` (`sh:RulesEntailment` runs all rules, as does a shapes graph without `sh:entailment`), and prefixes declared at the shapes graph. Shapes typed `sh:ShapeClass` are node shapes with an implicit class target. Not supported: `sh:expectedPredicate`, temporary triples and `sh:sourceRule`, which need RDF 1.2 triple terms, and the order dependent node expressions (`limit`, `offset`, `orderBy`, `findFirst`, `flatMap`, `matchAll`, `nodesMatching`). The W3C SHACL 1.2 inference rules tests and the TopBraid DASH SHACL-AF rules tests are included in the tests. Inferred triples that are already in the data graph are no longer reported as inferences
- SPARQL-RL 1.2 (maplib Enterprise Edition): `Model.infer` takes rule sets in the SPARQL-RL syntax of the W3C Data Shapes Working Group (`RULE { ... } WHERE { ... }`, `DATA { ... }`, `NOT`, `NOT DATA`, `WHERE DATA`, `SET(?x := ...)`, `GROUP BY ... { ... } [ ?n := COUNT(*) ]`), checks their well-formedness and stratification, and evaluates them stratum by stratum as the specification defines. `IMPORTS` is not supported. The W3C SPARQL-RL syntax, well-formedness, stratification and evaluation tests are included in the tests
- Object storage: `Model.read`, `read_template`, `write`, `write_cim_xml`, `serialize` and `deserialize` take URLs of Google Cloud Storage (`gs://bucket/path`), Azure Blob Storage (`az://container/path`, `abfss://container@account.dfs.core.windows.net/path`, `https://account.blob.core.windows.net/container/path`), Amazon S3 (`s3://`), HTTP(S) and `file://`, as well as local paths. Credentials are found as the cloud SDKs find them (environment variables, the metadata server on Google Cloud, managed and workload identities on Azure), or are given with the new `storage_options` argument, with the option names of Polars' `storage_options`. Files that are read are downloaded to a temporary file first, with concurrent range requests for large files. Files that are written are uploaded as they are written, in concurrent parts, and the object only appears when the write completes
- `maplib.storage` stores raw bytes in object storage and local files, with the URLs, credentials and `storage_options` of `Model.read` and `Model.write`: `put(url, data, if_match=None, if_none_match=False)` returns a version token (the ETag, with the object generation on Google Cloud Storage), `get(url)` returns the bytes and their token, and `head`, `exists`, `delete` and `list(prefix_url)` (names, sizes, times, tokens) are there for garbage collection. `put` with `if_match` replaces the object only if it is still at that version and raises `storage.PreconditionFailed` otherwise, and `if_none_match=True` raises `storage.AlreadyExists` if there is an object, so that several writers can publish a manifest with optimistic concurrency. S3, Google Cloud Storage (as generation preconditions; the version from `list` has no generation there, so use the token of `get` or `head` for `if_match`), Azure and the local file system support both; for local files `if_match` is emulated with a lock file, which serializes the writers on one machine only. Plain HTTP raises `storage.NotSupported`. A missing object raises `storage.NotFound`, a `FileNotFoundError`. In Rust, `RemoteLocation::put_with`, `get_with_version`, `info`, `list_info` and `parse_path_or_url`
- `Model.serialize(url)` writes a single file locally and uploads it. `Model.serialize(url, single_file=False)` writes a folder to a new generation under the URL (`gen-<time>-<id>/`) and then publishes it by replacing the object `LATEST` with its name, with a conditional put: readers see the previous or the new model whole, and if another writer published to the URL in the meantime, the serialization fails instead of replacing it. The current and the previous generation are kept
- Triple tables in object storage (maplib Enterprise Edition): `Model.deserialize(url, storage="disk", storage_folder=...)` on a folder serialized to object storage does not download the triple tables, only the dictionaries and the sparse indices. Each table is downloaded to the storage folder the first time it is read. With `cache_size` (or `MAPLIB_REMOTE_CACHE_BYTES`), the least recently read downloaded tables are removed when they take more space, and downloaded again when read. Tables read in the last five minutes (`MAPLIB_REMOTE_CACHE_GRACE_SECONDS`) are kept, as running queries may read them. So a disk mode model can be served from a VM or container with a local disk smaller than the model. Triples added afterwards stay local until the model is serialized again. Serializations record the number of triples of each table for this; folders written by earlier versions are downloaded when deserialized
- In Rust, `file_io::remote` has `RemoteLocation`, `Input` and `Output` for object storage, `SerializationSource`, `SerializationTarget` and `SerializedFile` have `Remote` variants, `Triplestore` and `Model` have `serialize_triples_remote` and `deserialize_triples_remote`, and `Triples::from_serialization` takes the number of triples when it is known. The metadata of a serialization folder is written after its other files
- The config graph configures the query result cache of the model (`mcfg:QueryCache`, see `CONFIG_GRAPH.md`): `maplib.config.QueryCacheConfig` with `write_query_cache`, `read_query_cache`, `remove_query_cache` and `apply_query_cache` keeps whether it is enabled, its limits (entries, bytes, the largest result kept), a ttl, the shortest run time worth keeping and whether results over virtualized databases are kept. `apply_config` sets it with `Model.set_query_cache`
- `maplib.config` and the Model portal's Connect page configure InfluxDB: InfluxDB 3 (`influxdb`, `mcfg:InfluxDBDatabase`, resources are SQL over measurements) and InfluxDB 2 / 1.8 with Flux (`influxdb2`, `mcfg:InfluxDB2Database`, resources are measurements: the options or connection parameters `measurement`, `id` and `field`). The token is a secret. Probing without SQL lists the measurements
- CSV on the Web ([#26](https://github.com/DataTreehouse/maplib/issues/26)): `Model.map_csvw(source, metadata=None, graph=None, minimal=False, iri_mappings=None)` converts tabular data to RDF as specified by the W3C CSVW recommendations ([tabular data model](https://www.w3.org/TR/tabular-data-model/), [metadata](https://www.w3.org/TR/tabular-metadata/), [csv2rdf](https://www.w3.org/TR/csv2rdf/)), in standard or minimal mode. The source is a metadata document or a CSV file, for which the metadata is located as in the specification (with the site-wide configuration `/.well-known/csvm` if it is found, else `<file>-metadata.json` and `csv-metadata.json`) or taken from the header row. Dialects, inherited properties, datatypes with formats (numbers, booleans, dates and times, regular expressions) and constraints, lists (ordered as `rdf:List`), virtual and suppressed columns, notes and common properties, row titles and foreign key validation are supported. The tables are added to temporary graphs using Facade-X, and a SPARQL Update generated from the metadata builds the output (URI templates are compiled to SPARQL expressions) and drops the temporary graphs. The update is returned. Warnings (invalid metadata properties, invalid cell values and values that maplib can not store with their datatype, such as dates with time zones, which are output as strings) are issued as Python warnings. - `Model.serve()` (maplib Enterprise Edition) serves the model over the SPARQL 1.1 Protocol and Arrow Flight at the same time, in the background, on the model itself, so changes made from Python and through the endpoints are seen by both. Queries through the endpoints run at the same time as each other and as read operations from Python, while updates wait for exclusive access. It returns a `Server` with the endpoint URLs, `stop()`, `wait()` and context manager support. The SPARQL endpoints (`/sparql`, `/query`, `/update`) follow the W3C SPARQL 1.1 Protocol, including `default-graph-uri`, `named-graph-uri`, `using-graph-uri` and `using-named-graph-uri`, content negotiation (JSON, XML, CSV, TSV and Arrow IPC results, Turtle, N-Triples, RDF/XML, JSON-LD, N-Quads and TriG graphs) and the service description. `/store` implements the SPARQL 1.1 Graph Store HTTP Protocol. Other web sites can not read results or send updates unless allowed with `cors_origins`, and on loopback addresses requests with another Host are refused, against DNS rebinding. LOAD and SERVICE are refused, so clients can not make the server fetch URLs or read files. The Flight features are also served over plain HTTP at `/arrow` on the SPARQL port (`arrow_http=True`), for networks where gRPC does not get through. `Model.query(query, endpoint=server.url, endpoint_token=...)` queries a served model and returns the same results as `Model.query()` on it, with maplib's own types sent as Arrow over HTTP. Arrow results are zstd compressed within the Arrow format for clients on other hosts (`arrow_compression="auto"`, or `"zstd"` / `"none"`, also per request), and other responses are gzip compressed on request. HTTP/1.1 and HTTP/2 are served. Request sizes are limited by `max_request_bytes`. - SPARQL 1.1 Federated Query: `SERVICE <endpoint> { ... }`, `SERVICE SILENT` and `SERVICE ?endpoint` (with the variable bound before the SERVICE) in queries and updates. The pattern is sent to the endpoint with the SPARQL 1.1 Protocol and its results (SPARQL JSON, XML or TSV, with their RDF types and unbound values) are joined with the rest of the query, also within OPTIONAL, UNION, MINUS and FILTER. SERVICE is evaluated after the local patterns of its group, and the distinct values that they bind for the shared variables are sent with the pattern as VALUES blocks (a bind join, `batch_size` rows per request, `concurrency` requests at a time), so that the endpoint only returns matching solutions; the bindings of the left side of an OPTIONAL are sent to a SERVICE in the optional part. When the endpoint is a maplib server (`Model.serve()`, maplib Enterprise Edition), the results come in maplib's own Arrow format, and the bindings are sent as Arrow too, in batches of `arrow_batch_size` rows. `SERVICE SILENT` gives a single empty solution when the endpoint fails, times out or can not be reached. `Model.set_federation(allowed_endpoints=None, headers=None, timeout=300, max_rows=None, batch_size=1000, arrow_batch_size=1000000, concurrency=4, method="POST", bind_join=True, allow_load=False)` sets which endpoints may be reached (by URL prefix, any http(s) URL by default), headers per endpoint (e.g. a bearer token), the timeout and a row limit per SERVICE; redirects are only followed to allowed URLs. Refused endpoints and too many rows are errors also with SILENT. In Rust, the client is `external_sparql::federation`, `Triplestore::federation` holds the settings, `QuerySettings::federation` overrides them, and `Model::query_with_federation` and `update_with_federation` take them
- SPARQL Update `LOAD <url> [INTO GRAPH <g>]` and `LOAD SILENT` read an RDF file from an http(s) URL (the format from the media type of the response, else from the extension of the URL), object storage (`s3://`, `gs://`, `az://`) or a `file://` URL (only when listed explicitly in `allowed_endpoints`), into the default graph or the given graph. LOAD is refused unless enabled with `Model.set_federation(allow_load=True)`, and only reaches the allowed endpoints
- `Model.serve()` (maplib Enterprise Edition) refuses SERVICE and LOAD unless allowed: `serve(service_endpoints=[...])` lists the endpoints that SERVICE in queries and updates sent to the server may reach (`["*"]` for any http(s) URL), with the other federation settings of the model, and `serve(allow_load=True)` allows LOAD of those URLs (with `allow_update`). Refused requests get 403. `/sparql` also gives SELECT results in maplib's solution mappings format (`application/vnd.maplib.solution-mappings`) when asked for, and `POST /arrow/query` takes PVALUES parameters as Arrow, sent after the query command (`application/vnd.maplib.parameterized-query`), as used by SERVICE from another maplib
- The W3C SPARQL 1.1 federated query tests (`sparql11/service`) are included in the tests, run against local mock endpoints with SPARQL JSON, XML and TSV results
- Function calls in templates: template arguments can be computed with SPARQL functions, written Lisp-style as in Frog (M. Jarholt, "Frog: Functions for ontologies — An extension for the OTTR-framework", Master's thesis, University of Oslo, 2022, https://hdl.handle.net/10852/96925), e.g. `ottr:Triple((IRI (CONCAT "http://example.net/" ?id)), rdfs:label, (UCASE ?name))`. The functions are the SPARQL built-in functions and operators, XSD casts such as `(xsd:integer ?x)`, UDFs, Frog's base functions that have a SPARQL counterpart, and functions defined in stOTTR documents with Frog's `def` syntax, e.g. `def ex:toIRI(xsd:string ?id) -> ottr:IRI :: (IRI (CONCAT "http://example.net/" ?id)) .`, which are inlined. Function calls are evaluated by the SPARQL expression engine over all rows of an instance at once, before list expansion. A call that gives no value (an error, as in SPARQL) is `none`: optional parameters are left out, defaults are used, and otherwise the instance is not expanded. Function calls can not be list expanded or take lists, and defined functions can not be recursive. In Python, `FunctionCall("CONCAT", [...])` is a term for `Argument`, `Instance` and `Triple`. In Rust, `StottrTerm::FunctionCall`, `Statement::Function`, `TemplateDataset::functions` and `templates::functions`. In the templates of virtualized resources (maplib Enterprise Edition), the function calls are evaluated on the rows the virtualized database returns, and filters on their values are not pushed down
- stOTTR documents can give `none` as an argument or default value, which is how templates with a `None` argument are printed

- Shortest paths: the magic predicate `maplib:shortestPath` (`https://datatreehouse.github.io/maplib/vocab#shortestPath`) finds the shortest paths from a source to targets, with their length, cost and nodes, in SPARQL queries. Its options are named as those of the length-constrained `maplib:path`. The sources, targets (`maplib:object`) and nodes to avoid (`maplib:avoid`) are the values the other patterns of the group give their variables, or constants, and an unbound object means every node reached. Options: `predicate` and `inversePredicate` (the edges and their direction), `anyPredicate "forward"|"backward"|"both"` (every predicate whose objects are IRIs or blank nodes, except `rdf:type`) with `excludePredicate`, `minLength` (default 1), `maxLength`, `limit` (the nearest targets of each source), `weight` and `defaultWeight` (node costs, Dijkstra), `maxCost`, `kShortest` (k shortest simple paths, Yen) and `allShortest` / `maxPaths`; outputs `length`, `cost`, `pathIndex`, `pathNodes` (a JSON array), and one row per node with `pathNode`, `nodeIndex`, `stepPredicate` and `stepInverse`. The search runs on an integer graph of the edge predicates in compressed sparse rows, cached until their triples change, with bidirectional breadth first search for single targets, early stopping, and parallel searches from different sources. See the README
- DuckDB sandbox (maplib Enterprise Edition): `DuckDBDatabase(..., sandbox=True, allowed_directories=..., allowed_paths=...)` turns off DuckDB's `enable_external_access` and sets `lock_configuration` before any resource SQL runs, so the SQL of a resource (or given to `maplib.config.probe`) can not read local files (`read_csv('/etc/passwd')`), `ATTACH` other databases, `COPY` to files, install extensions or `SET enable_external_access = true` again. The database file stays usable, as do the allowed directories (with subdirectories) and files. `maplib.config` takes `sandbox`, `allowed_directories` and `allowed_paths` as parameters of a `duckdb` virtualization, and `probe` connects in the same sandbox as `apply_virtualization`. The sandbox is opt-in, so existing models whose resource SQL reads files next to the database (e.g. `read_parquet`) keep working; it is recommended whenever users who should not read the process's files can configure a virtualization. A deployment enforces it with the environment variable `MAPLIB_DUCKDB_SANDBOX=1`: every `DuckDBDatabase` is then sandboxed, `sandbox=False` is refused, the database file must already exist (no files are created through `database`), and the database file and the allowed directories and paths must lie in `MAPLIB_DUCKDB_ALLOWED_DIRECTORIES` (separated by `os.pathsep`; when it is unset, no further directories can be allowed). `FabricLakehouseDatabase` is not sandboxed, as it needs extensions and network access
### Bug fixes
- The warning that full text search is only defined for named graphs or the default graph is no longer logged for queries that do not use full text search
- `maplib.add_triples(source, target, source_graph, target_graph)` copies the triple tables natively in Rust instead of mapping each predicate through a temporary template from Python, and keeps the blank nodes of the source distinct from those of the target: before, blank nodes with the same label in the two models (e.g. `_:b` read into each) were merged into one. Each copy from another model gets new blank nodes; a copy within one model (`source` and `target` the same, e.g. to copy a graph into another graph) keeps them, as the graphs of a dataset share blank nodes. In Rust, `Triplestore::copy_triples` and `Model::add_triples`
- Queries joining on two variables, where many solutions share the value of one of them, took memory quadratic in the number of solutions once a basic graph pattern had more than about 100 000 solutions: Polars' join reordering moved a join on only one of the variables first, e.g. the two `ua:BrowseName` patterns of `?type_child ua:BrowseName ?browse_name . ?instance_child ua:BrowseName ?browse_name`, so every instance child met every other child with the same browse name. The results were right. maplib now keeps the join order it chose from the patterns (`utils::polars::keep_join_order`). The OPC UA browse path query of the typing shapes for 100 000 instances with a common browse name needs 0.15 GB instead of over 134 GB
- Reading RDF/XML (also CIM/XML) bounds the expansion of `<!ENTITY>` declarations, so a small file with nested entities ("billion laughs") can no longer exhaust memory. An entity value may expand to at most 1 MiB, and all references to declared entities in a document to at most 10 MiB plus 10 bytes per input byte read, which ordinary use of entities for namespace IRIs (as in OWL files) stays far below. Exceeding a limit is a syntax error naming the entity. External entities (`SYSTEM`, `PUBLIC`) are still refused and never fetched. `Model.map_xml`, which also reads OPC UA NodeSet2 files, ignores the DOCTYPE and never expands declared entities, so it was not affected. In Rust, `RdfXmlParser::with_max_entity_expansion`, `with_max_total_entity_expansion` and `with_entity_amplification_factor` change the limits
- `Model.map_xml` (and the OPC UA NodeSet2 mapping, which uses it) lost the text at entity and character references: `<item>Pump &amp; motor &#65;</item>` gave the two literals `"Pump"` and `"motor"`. Character references and the five predefined entities (`&amp;`, `&lt;`, `&gt;`, `&apos;`, `&quot;`) are now resolved, and adjacent text, CDATA and references are joined into one literal, trimmed as a whole, so the example gives `"Pump & motor A"`. Other entity references, including entities declared in a DOCTYPE, are dropped and never expanded, as before
- Printing a `Template` parsed from stOTTR (`str`, `repr`, or the list from `Model.get_templates()`) panicked with "not yet implemented". Templates print their annotations as `@@` instances after the signature, and the printed text can be added again with `add_template`. Templates without annotations no longer get an empty annotation list from the parser
- Chrontext (maplib Enterprise Edition): a UNION of static patterns joined with time series, e.g. `{ ?w a A } UNION { ?w a B } ?w :hasTimeseries ...`, no longer returns every solution twice
- `maplib.virtualization.DuckDBDatabase` works with DuckDB 2, which has no `pl()` on the result of `execute`
- `Model.create_index` (and `maplib.config.apply_config`) creates the object indexes it is given for the triples already in the model, not only for triples added afterwards, and drops the object indexes of predicates that no longer have one. Sorting the stored triples by object takes about as long as adding them did. In Rust, `Triples::set_object_indexing` turns the object index of a triple table on or off
- The `expression` of a `Not` expression in `maplib.vq` was `None`, so virtualized queries with a negated filter could not be translated to SQL
- Virtualized queries with unary minus or plus (e.g. `ORDER BY DESC(?v * -1)` or `FILTER(-?v < 0)`) panicked with "not yet implemented" for Python databases (SQL databases, Kusto, OPC UA, Cognite). They are now `Expression.UnaryMinus` and `Expression.UnaryPlus` in `maplib.vq` and are translated to SQL and KQL; IRI constants are `Expression.IRI` (with `iri`), and other expressions that can not be passed to a Python database raise an error instead of panicking
- Length-constrained property paths: the `{n}`, `{n,m}`, `{n,}` and `{,m}` path syntax of Apache Jena ARQ (and of the SPARQL 1.1 drafts), e.g. `?s (ex:p|^ex:q){2,4} ?o`, with set semantics like the other paths, and the `maplib:path` magic predicate, e.g. `?s maplib:path [ maplib:predicate ex:p ; maplib:minLength 2 ; maplib:maxLength 4 ; maplib:object ?o ; maplib:length ?len ]`. It takes one or more predicates and inverse predicates (or any predicate), returns the length (`maplib:length`), only the shortest paths (`maplib:shortest true`) or the nodes of each path (`maplib:pathIndex`, `maplib:nodeIndex`, `maplib:pathNode`), and `maplib:pathMode "walk" | "acyclic" | "simple"` chooses whether paths may revisit nodes. Either end may be bound or unbound, and paths are searched from the bound end with a breadth-first search per start node over the numbered nodes, deduplicated per node and length. See the `maplib:path` section of API_USAGE.md. In Rust, `SparqlError::PathError` reports invalid options
- Zero-length property paths (`ex:p*`, `ex:p?`, `ex:p{0,n}`) from a variable bound by other patterns or by VALUES now match each of its values that is a node of the queried graph (a subject or object of some triple), as SPARQL 1.1 requires, also nodes without `ex:p` triples. Before, `?x a ex:Node . ?x ex:p* ?y` left out the nodes without `ex:p` triples
- Datalog (maplib Enterprise Edition): a rule whose BIND combines a variable of inferred triples with a variable of triples that no rule changes (e.g. `BIND(IRI(CONCAT(STR(?p), "_", STR(?n))) AS ?p2)`) inferred nothing after the first iteration, while `debug=True` gave the right result

- `Model.query_external` no longer panics ("entered unreachable code") on SELECT results where a variable is unbound in some rows, as with OPTIONAL. Unbound values are nulls, also before the first bound value, and a variable that is never bound is a column of nulls

In Rust, `triplestore::new_triples_by_predicate` merges new triples per predicate
- Reading, mapping and inserting triples could hang with no CPU use. The triple tables of different predicates and types are built, compacted and deleted from in parallel, and each of these steps queried its table with the streaming engine of Polars, which can wait for threads that the parallel steps have taken. They now use the in-memory engine, which is safe there and also avoids the fixed cost of a streaming query per table
- `Model.query(debug=True)` panicked with "not yet implemented" when a query with no results contains `GRAPH ?g { ... }`. ### Performance
`generate_templates` is implemented in Rust (`maplib::template_generator::generate_templates`) instead of Python, with the same templates, parameter names, order and types, and runs in about 60% of the time on FIBO.

Datalog and SHACL rule inference with many small iterations is faster, about 2× for a long chain of semi-naive iterations and 15-20% for the Datalog benchmarks: CONSTRUCT results, encoding of new solutions and small solution mappings are collected with the in-memory engine instead of the streaming engine, small rank sorts no longer use the thread pool, and an in-memory query result is picked up within a millisecond of being ready instead of up to 50 ms. Evaluating a triple pattern outside a named graph no longer logs a full text search warning when there is no full text index.

Disk storage answers lookups of all properties of a subject (`SELECT ?p ?o WHERE { <e> ?p ?o }`) about 10× faster: at 20 M triples, 7 ms instead of 86 ms, against 2 ms with memory storage. Lookups with a known predicate are about 2× faster. Decoding a few results no longer joins them with the whole IRI and literal dictionary (maplib Enterprise Edition), a bound subject or object is encoded once per triple pattern instead of once per predicate table, and the few row groups a bound subject needs are read directly instead of through a lazy scan per range. Queries that return many rows, such as LIMIT 100000, are as slow as before with disk storage (about 90 ms at 20 M triples, 3 ms in memory).

SHACL rules run on the datalog engine with semi-naive evaluation: when a rule runs again, it only joins the triples inferred since its last run with the existing ones, parts of the rule bodies that no rule can change are computed once, and rules whose inputs did not change are not run again. Previously each iteration ran every rule on all of its focus nodes, so recursive rules (e.g. transitive closures) and long rule chains took time quadratic in the number of iterations. This also holds when the inferred predicate is used inside a property path, as in `$this ex:child/ex:offspring? ?o`. Rules that only add triples (no OPTIONAL, MINUS, NOT EXISTS or aggregates) and share an order see each other's new triples in the same pass, so chains of such rules finish in fewer passes.

When inferences go to a separate graph, datalog and SHACL rules no longer compare inferred triples with the data graph for predicates that the data graph has no triples of. SHACL validation without rules no longer reads the shapes graph for rules, and finds parameter declarations with one query instead of a filter in each shape query.

In disk mode the triple tables and their deduplication index are no longer held in memory. With few triples per distinct IRI or literal (as in the CIM data), memory use is dominated by the dictionary and reading, and disk storage saves little.

Triple table segments are compacted much faster, which matters most for datalog, where every iteration adds a small batch of triples to tables that are often large:
- Size-tiered compaction: only the trailing segments of comparable size are merged with the new triples, so a large table is no longer rewritten every 11 inserts. A table has O(log n) segments (at most 16).
- Merging sorts packed rank keys with Polars instead of a value-by-value heap merge, and builds the object sort from the merged triples instead of also reading and merging the object sorts of the segments.
- Disk mode: new triples are deduplicated against only the row groups that may hold their subjects, found through the sparse subject index, instead of reloading every stored triple of the table into an index on each insert. Small trailing segments (under 16k triples) stay in memory until merged, so small inserts don't write and rewrite small parquet files.

Query results are collected with the Polars streaming engine, which the rest of maplib already used; until now the final step of a query ran on the in-memory engine. Whole-table scans and counts, large result sets and DISTINCT are faster, while small queries are about as fast as before. `MAPLIB_POLARS_ENGINE=in-memory` switches back to the in-memory engine.

`IN` with a list of IRIs looks the values up in a hash set instead of comparing with each IRI in turn, so long lists no longer slow a query down. The same holds for `IN` with a list of integers (of any integer datatype) when the left side holds integers of one integer datatype. Property paths with `*`, `+` and `?` map the computed paths back to IRIs and literals by position instead of with joins. Patterns without shared variables (also inside `OPTIONAL`) are combined with a parallel cross join instead of a join on a constant key, which ran on one thread.

After `Model.compact()`, subjects are marked as sorted, so DISTINCT and grouping on subjects are faster.

ORDER BY on IRIs and strings no longer collects its input in memory for each sort column, and with memory storage it ranks the values batch by batch, so large sorts are several times faster and spill to disk under the memory limit. ORDER BY with LIMIT or OFFSET, and joins and aggregations, still keep their working state in memory.

ORDER BY with a large LIMIT (with or without OFFSET; LIMIT plus OFFSET at least 10 000 and at least a thirty-second of the estimated solutions) is collected with the in-memory engine, which sorts much faster than the streaming engine when many rows are kept. Such queries are several times faster, and many times faster for some sort keys. Smaller LIMITs are left to the streaming engine, whose top-k is faster there. Their working state is kept in memory, so they do not spill to disk under the memory limit. `MAPLIB_POLARS_ENGINE=streaming` keeps the streaming engine for them.

`GRAPH ?g` in the templates of `Model.update` partitions the solutions by the encoded graph IRIs in one pass, and decodes one IRI per graph, instead of decoding every row and filtering the solutions once per graph.

Deleting triples that are not in a table no longer rewrites the table, so DELETE DATA and DELETE WHERE of absent triples leave the stored triples and their indexes as they are. The count of deleted triples that decides when memory storage is compacted counts only the triples that existed.

Tantivy answered exact matches from its term dictionary, but scanned all strings for substring matches, which it ran whenever the exact matches did not fill the limit. DuckDB scans the strings once per query for both. Reading without full text search is unchanged.

Faster encoding and decoding with in-memory dictionaries:
- Reading, mapping and inserting encode string columns directly with global codes: all values are looked up in the dictionary in parallel, the new ones are deduplicated in parallel and added once with consecutive codes. Before, each column got its own local dictionary, which was then merged into the global dictionary and its codes re-encoded. Hybrid and disk storage keep the previous path.
- Repeated values next to each other are looked up once, and constant columns (e.g. from templates) are encoded once instead of once per row.
- Query results and formatted values (`<iri>`, `_:blank`, `"string"`) are decoded straight into string arrays in parallel, without building a string per value first.

(Medians of 2 runs alternating with the build before this change. The v0.21.0 column uses v0.21.0 runs from an earlier round on the same machine.)

Faster lookups, property paths and small inserts:
- Property paths (`+`, `*`, `?`) with a bound end, a constant IRI or a variable whose values are known from VALUES or earlier patterns, follow the paths from those nodes only, step by step, instead of computing the transitive closure of the whole graph and filtering it.
- The values of a pattern's variables are pushed down from solution mappings of up to 100 000 rows (was 500). Lookups of many values walk the sorted values and the sparse index together instead of searching the index once per value, and read an in-memory table with one gather instead of one slice per range. When the ranges cover more than half of a table the whole table is read, and at most 256 ranges of a stored table are read.
- A small insert or delete into a large in-memory table without a deduplication index checks only the stored triples with the same subjects, instead of indexing every triple of the table first.

Reading and writing HDT is much faster. Reading decodes each term of the HDT dictionary once and maps it directly into the model's dictionaries, then adds the triples as integer IDs in parallel batches, without building HDT query indexes. Writing deduplicates and maps triples using the model's dictionary codes, decodes only the distinct terms, and writes the triples section without building query indexes. The written files are unchanged. On a CIM model of 2.2 million triples, reading takes 0.28 s instead of 3.41 s in v0.20.32 (12x faster) and writing 0.20 s instead of 5.69 s (28x faster)

### Bug fixes
- SPARQL: `+`, `-`, `*` and `/` were parsed as right associative, so `8 - 3 - 2` gave 7 and `12 / 2 / 3` gave 18. Operators of the same precedence are now left associative, as the SPARQL grammar specifies. Serialized queries put arithmetic in parentheses, so that `8 - (3 - 2)` and `(1 + 2) * 3` keep their meaning
- Ctrl-C now stops a running query. Before, a long query could keep running until it finished
- `STRDT` with `xsd:dateTime` or `xsd:dateTimeStamp` dropped the time zone, e.g. `STRDT("2015-03-15T15:02:37-05:00", xsd:dateTime)` gave `"2015-03-15T20:02:37"`. The time zone is now kept, also when the values have different time zones
- A triple pattern with the same variable in two positions (e.g. `?s <p> ?s`) panicked, in queries and in `DELETE WHERE`, when the predicate also had triples where the two positions had different types (e.g. blank node subjects with IRI objects)
- Hybrid storage: `Model.compact()` (also run by `Model.serialize()`) failed with a DuckDB "Duplicate key" error once the dictionary had to be renumbered, e.g. after more than ten inserts into the same predicate
- SHACL rules: a rule that re-asserts a triple already in the data graph no longer makes inference loop until `max_iterations` (or forever with one rule). Inserting transient triples that all already existed non-transiently dropped the earlier transient triples with the same predicate, which were then inferred again on every iteration ([#76](https://github.com/DataTreehouse/maplib/issues/76))
- SHACL rules: rules whose WHERE clause has no triple pattern on `$this` (only `OPTIONAL` / `BIND`) now also run for focus nodes that become targets of their shape after the rule first ran ([#77](https://github.com/DataTreehouse/maplib/issues/77))
- SHACL: shapes with several `sh:message` values (e.g. one per language) lost the results of property shapes, so data violating them was reported as conforming, kept only one of the messages of node shapes, and gave one result per message for SPARQL constraints. Every result now has all the messages of its shape as `sh:resultMessage` values. Property shapes with several `sh:name` or `sh:description` values also lost their constraints ([#86](https://github.com/DataTreehouse/maplib/issues/86))
- HDT: writing the same model twice could give different files, as the properties of the triples section's control information were written in random order
- HDT: literals are written with their values as they are, as hdt-java and hdt-cpp do, rather than N-Triples escaped, so other HDT tools no longer read a tab as `\t`. Reading takes a backslash in a literal of a file from hdt-java or hdt-cpp as part of the value, rather than as the start of an escape. Files written by earlier maplib versions are recognised and still read correctly. Writing a literal that contains U+0000 raises an error, as HDT cannot store it
- HDT: the header of written files describes the dataset with the same vocabulary as hdt-java and hdt-cpp: IRIs for the dataset types and the dictionary and triples formats, and `hdt:publicationInformation` for the publication information
- Full text search: with a fixed subject (`ex:a maplib:fts ?fts`), the limit was applied before filtering on the subject, so few or no results were returned. Triples deleted with SPARQL Update were still found, now they are no longer found after `Model.compact()`. An on-disk index no longer leaves a folder behind for every index created
- Pretty Turtle and RDF/XML: the rdf:first and rdf:rest triples of blank nodes that do not form a well-formed list were not written, e.g. of a list without rdf:nil, a list node with two rdf:first, or a list whose later node is also referred to by another triple (shared or cyclic lists). Only lists where each node has one rdf:first and one rdf:rest, and every node after the first is only referred to by the rdf:rest before it, are written as lists; other rdf:first and rdf:rest triples are written as any other triples
- Pretty RDF/XML of several graphs in one document (as for CIM/XML): a blank node used in more than one of the graphs could be nested or written as part of a list in one graph, so that the other graphs referred to a blank node that was not in the document. Such blank nodes are now written with their label

## v0.21.0
### Performance
Besides the changes listed below, the memory improvements earlier in this release contribute to the faster reading and SHACL validation.

- RDF/XML is parsed in parallel, by splitting the document between top-level elements. The RDF/XML parser from Oxigraph (oxrdfxml) is now included in maplib to make this possible
- RDF/XML is written with a new pretty serializer (see Features)
- CIM/XML is written by building temporary graphs with two SPARQL queries driven by the profiles (one for the instances of the profile classes, one for their profile properties) and writing them with the pretty RDF/XML serializer, instead of running queries per class and property
- Disk-backed models keep their category map databases open instead of opening a database for every lookup, which makes small queries about ten times faster
- Inserting triples no longer ranks the inserted values against the whole dictionary, which made every insert cost time proportional to the number of distinct IRIs and literals in the model. This was most of the per-iteration cost of datalog inference
- The sort order of the dictionary is cached between ORDER BY queries and datalog iterations, until new values are added
- Removed debug output that SHACL validation printed for every sh:class constraint (it also evaluated the constraint a second time)

### Breaking changes
- The `streaming` parameter is removed from `Model.query`, `Model.update`, `Model.insert`, `Model.validate`, `ValidationReport.results` and `ValidationReport.details`. Polars already runs lazy queries with its streaming engine, so the parameter had no effect (benchmarks with `streaming=True` and `streaming=False` were identical). Remove the argument from calls
- RDF/XML (and CIM/XML) is read in parallel by default (`parallel=None`). Pass `parallel=False` to read sequentially. Line numbers in parse errors may refer to the position within a chunk of the document
- RDF/XML output is now formatted differently (one element per subject, nested blank nodes), but contains the same triples
- `write_cim_xml` writes CIM/XML as IEC 61970-552 / CGMES requires (see Bug fixes). Objects are identified relative to the document (rdf:ID="_<mRID>", rdf:resource="#_<mRID>"), so read the files with the same `base_iri` as the original data, as for any CGMES file

### Features
- `write_cim_xml` uses the pretty RDF/XML serializer. The exported triples are the same as before (the FullModel header first, then one typed element per instance with the properties its class has in the profiles, literal values as plain strings), but elements and properties are ordered differently
- Pretty RDF/XML serializer, working like the pretty turtle serializer: one node element per subject with all its properties, typed node elements when the type has a prefix, blank nodes that are used once nested where they are used, RDF lists written with rdf:parseType="Collection" when possible, and all namespaces declared on the root element
- ASK queries. m.query() returns a bool, or a SPARQL JSON boolean result with return_format="json"
- isNUMERIC and RAND SPARQL functions
- SHA256, SHA384 and SHA512 SPARQL functions
- Read and write TriG and N-Quads (format "trig" / "nquads", or the .trig / .nq file extensions when reading). Writing these formats outputs all graphs unless a graph is specified

### Bug fixes
- `write_cim_xml` was not compliant with IEC 61970-552 / CGMES (also before this release):
  - Objects were written with absolute IRIs (rdf:about="urn:...:#_<mRID>"); they are now rdf:ID="_<mRID>" with rdf:resource="#_<mRID>" references, when all objects share one base IRI
  - Enumeration values (e.g. cim:WindingConnection.Y) were written as objects when the vocabulary was in the data graph
  - Objects that also had superclass types (e.g. cim:Equipment) were written once per type; they are now written once, as their most specific class
  - Association ends that the profiles mark as not used (cims:AssociationUsed "No") are never written, and the used end is derived from them when the data only has the unused end
  - Only the namespaces that are used are declared, and the default Model.created / Model.scenarioTime are UTC with whole seconds (e.g. 2021-02-02T22:28:41Z)
- Disk-backed models wrote subjects on the boundaries between internal segments twice when writing turtle or RDF/XML (giving invalid RDF/XML with a duplicate rdf:ID)
- Writing turtle could hang forever (a deadlock between the pretty turtle writer's parallelism and Polars), e.g. for CGMES/CIM models
- sh:not required every constraint of its shape to fail, instead of the shape not conforming. Combined with sh:or this gave false results, e.g. 363 false sh:or results when validating CGMES shapes against the SHACL-SHACL shapes (pyshacl agrees there are none)
- sh:not with a shape that has several constraints of which some pass and some fail (e.g. two sh:class values) treated the shape as conforming, giving false sh:not results
- Inserting triples could drop triples whose values had been re-encoded in the dictionary, as their values could not be ranked when sorting
- Removed the pyarrow <24.0.0 pin. pyarrow only publishes Python 3.15 wheels from 26.0.0, so the pin made maplib uninstallable on Python 3.15
- COUNT now returns xsd:integer (Int64) as required by the SPARQL 1.1 spec, instead of xsd:unsignedInt (UInt32)
- SUM, AVG, MIN and MAX now work when the aggregated variable has multiple types. SUM and AVG promote the numeric types in each group (integer < decimal < float < double) and are unbound if a group contains a non-numeric value, MIN and MAX use the SPARQL ordering and keep the type of the selected value
- Division follows SPARQL op:numeric-divide: integer / integer gives xsd:decimal (e.g. 5 / 2 = 2.5, previously truncated to 2.0 as xsd:double), mixed types are promoted (decimal < float < double), and decimal division by zero is an error (unbound)
- COALESCE over arguments of different types returns the first bound argument (previously a value of a later argument could be returned nondeterministically)
- Fix panic when combining lang strings with differently encoded categoricals (e.g. COALESCE(?langString, "x"@en))
- Infinite xsd:double and xsd:float values are written as INF and -INF (previously inf and -inf, which are not valid lexical forms) in query results, STR() and all RDF serializations
- DATATYPE() of an unbound value or an error is unbound (previously the datatype of the variable was returned)
- YEAR, MONTH, DAY, HOURS and MINUTES return xsd:integer and SECONDS returns xsd:decimal including fractional seconds (previously xsd:unsignedInt, dropping fractions)
- STR() of xsd:dateTime and xsd:date values gives the XSD lexical form (e.g. 2010-06-21T11:28:01+00:00 instead of 2010-06-21 11:28:01.000000+00:00)
- Triple patterns without variables (e.g. { :s :p :o }) never matched. They now give one solution if the triple exists
- GROUP_CONCAT concatenated internal codes instead of the string values, and used an empty default separator instead of a single space. It now concatenates the string values (as STR()) of any type, including lang strings
- ABS, CEIL and FLOOR work when the argument has multiple types, and CEIL and FLOOR keep the type of the argument (previously xsd:integer)
- CONCAT accepts zero or one arguments
- Casting a blank node (e.g. xsd:double(?x)) gives an unbound value instead of failing the query
- FILTER, IF, NOT (!), AND (&&) and OR (||) use the effective boolean value of their operands (SPARQL 1.1 17.2.2): numbers are true unless zero or NaN, strings are true unless empty, and other values are errors. Previously a non-boolean FILTER failed the query, and IF with an error condition took the else branch instead of being unbound
- Casts to xsd:boolean, xsd:integer, xsd:decimal, xsd:float and xsd:double follow the XPath casting rules: strings must have a valid lexical form (e.g. xsd:boolean("abc") and xsd:integer("1.5") are unbound, previously false and a number), booleans can be cast to xsd:decimal, NaN and infinite values cast to integers or decimals are unbound, and casting other types such as dateTimes to numerics is unbound
- xsd:string() of a decimal gives the canonical form (e.g. "2.5"), not the stored representation with padding zeros
- "1"^^xsd:boolean and "0"^^xsd:boolean are valid booleans (previously rejected when parsing)
- STRBEFORE and STRAFTER accept a language tagged second argument when it is compatible with the first argument, and give the simple literal "" when there is no match, as required by the SPARQL 1.1 spec
- REPLACE keeps the language tag of its first argument
- CONCAT only gives a language tagged result when all arguments have the same language tag, and is unbound when an argument is unbound or not a string
- COUNT(DISTINCT *) is supported, and COUNT(*) works for patterns without variables
- SELECT * over a pattern without variables (e.g. { :a :b :c }) no longer panics
